# 동시 요청 부하 측정과 병목 수정

API 서버 없이 여러 OS 스레드가 같은 `Db`에 실제 SQL을 요청한다.
엔진의 동시 처리와 응답 지연을 검사하며, HTTP 서버나 요청 큐의 처리 용량을 측정하는 도구는 아니다.

## 재현

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build.ps1 -Test
.\build\db_load.exe build/my-load 100000 2000 16 3 1
```

```sh
make
./build/db_load build/my-load 100000 2000 16 3 1
```

인자는 다음 순서다.

```text
db_load 새디렉터리 [초기행수=100000] [요청수=2000] [최대스레드=16] [반복=3] [동기쓰기=1] [패턴=all]
```

- 최대 스레드 수 이하의 1, 2, 4, 8, 16, ...을 측정한다. 최대 64개다.
- 패턴은 `all`, `point`, `mixed90_10`, `scan_mix`, `slow_callback` 중 선택한다.
- 여러 스레드가 시작 게이트에서 대기한 뒤 함께 출발한다.
- 요청 수는 스레드당 수가 아닌 **한 케이스의 전체 수**다. 요청 번호를 스레드에 순환 배분한다.
- 모든 케이스는 같은 seed DB를 복사한 뒤 시작한다. 기존 DB의 누적 증가 효과를 배제한다.
- 디렉터리는 반드시 새 경로여야 한다. 기존 경로에는 덮어쓰지 않는다.
- 케이스 종료마다 재시작 검증하고 그 케이스의 임시 DB·잠금 파일만 지운다. seed DB와 CSV는 유지한다.
- `sync=1`은 문장마다 fsync/_commit을 유지한다. 성능을 위해 내구성을 낮추지 않았다.
- 준비·복사·워밍업·재시작 검증은 처리량과 쿼리 지연 측정에서 제외한다.

## 작업 패턴

| 패턴 | 요청 |
|---|---|
| point | 기존 ID 1건 조회 100% |
| mixed90_10 | ID 조회 90%, 단건 INSERT 10% |
| scan_mix | mixed에서 250번째마다 조회 하나를 고유 name 전체 스캔으로 교체 |
| slow_callback | mixed에서 250번째마다 조회 하나의 행 콜백이 50ms 대기 |

2,000개 요청에서는 mixed 계열마다 INSERT 200개,
scan/slow 패턴에서는 전체 스캔 또는 느린 콜백이 각각 8개다.
name과 ID 조회는 모두 기대한 고유 레코드 1개를 반환하는지 검증한다.

각 작업 스레드는 자신의 이전 호출이 끝난 다음 요청을 보낸다. 따라서 **closed-loop 측정**이다.
지정한 초당 도착률로 계속 요청을 밀어 넣는 open-loop 부하와 다르며, 서버 대기열 폭주나
타임아웃, 네트워크 지연, coordinated omission을 포함한 외부 서비스 SLO를 검증하지 않는다.

## 지표와 정확성

- `ops_per_second`: 전체 요청 수 / 게이트 개방부터 모든 worker 완료까지의 시간.
- p50/p95/p99/max: 파싱·락 대기·읽기/쓰기·콜백을 포함한 요청 지연(ms).
- `lock_wait_p95_ms`: 요청별 락 획득 대기 시간 합계의 p95.
- `lock_hold_p95_ms`: SELECT의 짧은 인덱스/스냅샷 임계 구간 합계 또는 INSERT의 writer mutex 보유 시간 p95.
- INSERT의 writer mutex 보유에는 디스크 기록과 공개 잠금 대기가 들어간다.
  중첩된 잠금 측정이므로 wait와 hold를 더해서 전체 지연이라고 해석하면 안 된다.
- 작업 종류별 p95도 출력한다. 전체 p95만 보면 드문 전체 스캔·느린 콜백이 가려질 수 있다.
- `errors`: SQL 실패, 기대 ID·name 불일치, 잘못된 반환 행 수 등.
- INSERT ID의 중복·누락, 재시작 후 전체 행 수, 삽입된 각 행의 name/age/ID를 검증한다.
- 재시작 자체가 모든 레코드의 체크섬과 연속 ID도 검사한다.

절대 지연 임계값은 단위 테스트에 넣지 않았다. 실행 장비·OS 스케줄링·동기화 지연에 민감해
시간 기준 통과/실패가 불안정해지기 때문이다. 정확성은 테스트로, 성능은 반복 측정으로 평가한다.

## 발견한 문제와 변경

기존 구현은 SELECT 전체와 결과 콜백 동안 테이블 읽기 잠금을 유지했고,
FILE의 공유 커서를 mutex로 보호했다. INSERT는 디스크 동기화 중에도 테이블 쓰기 잠금을 유지했다.

ID 조회만 보내도 공유 커서에서 직렬화됐고, 랜덤 조회마다 stdio 읽기 버퍼가 다시 채워졌다.
스캔·느린 콜백은 INSERT를 막았으며, 반대로 디스크 동기화는 SELECT를 막았다.
그래서 스레드가 증가해도 처리량은 잘 늘지 않고 tail latency가 커졌다.

수정은 두 단계로 진행했다.

1. **위치 지정 읽기와 짧은 SELECT 잠금**
   - Windows OVERLAPPED 읽기, POSIX pread로 공유 읽기 커서를 제거했다.
   - 단건 조회는 필요한 208바이트만 요청한다. 스캔은 256개 레코드씩 읽는다.
   - SELECT 시작 시 공개된 행 수를 확보하고, 파일 읽기·행 콜백은 잠금 밖에서 수행한다.
   - 범위 조회는 최대 256개 오프셋을 복사하고 잠금을 해제한다. 노드 포인터는 잠금 밖에 보관하지 않는다.
2. **쓰기 직렬화와 공개 잠금 분리**
   - writer mutex로 INSERT끼리의 순서와 ID·파일 상태를 보호한다.
   - 파일 기록·동기화 중에는 기존 레코드 SELECT가 진행할 수 있다.
   - 동기화 후 짧은 테이블 쓰기 잠금으로 인덱스를 갱신하고 published_rows를 공개한다.
   - 읽기 스냅샷은 published_rows까지만 보므로 미완료 INSERT가 먼저 보이지 않는다.

이 방식은 **레코드를 수정·삭제하지 않는 append-only 엔진**이라는 전제가 있어 가능하다.
UPDATE/DELETE를 추가할 때는 그대로 재사용할 수 없고 레코드 버전과 수명 관리가 필요하다.

Windows 읽기는 요청별 독립 OVERLAPPED와 완료 event를 사용하고,
완료를 확인한 뒤 버퍼·이벤트를 해제한다. API 제약은
[Microsoft ReadFile 문서](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-readfile)를 확인했다.

- [수정 전](load-before.csv): 테이블 전체 잠금 + 공유 읽기 커서.
- [1차 수정](load-after.csv): 위치 지정 읽기 + SELECT 스냅샷.
- [최종 수정](load-final-isolated.csv): writer mutex와 공개 잠금까지 분리.

최종 측정 수치는 아래에 기록한다. 세 실행의 처리량 중앙값과 **실행별 p95의 중앙값**을 사용한다.
세 실행 전체를 합쳐 계산한 p95는 아니다. 같은 장비에서도 스케줄링·페이지 캐시·디스크 동기화에
따라 변동이 있으므로 모든 원본 실행을 함께 남겼다.

Windows x64 / i5-8265U / MSVC C11 `/O2`에서 초기 데이터 10만 건,
케이스당 2,000요청, 스레드별 3회, 동기 쓰기 활성화로 측정했다.
최종 비교 실행은 빌드·ASan 테스트를 동시에 실행하지 않고 진행했다.

| 16스레드 패턴 | 수정 전 처리량(req/s) | 수정 후 처리량(req/s) | 수정 전 전체 p95(ms) | 수정 후 전체 p95(ms) |
|---|---:|---:|---:|---:|
| ID 조회 | 2,863 | 84,973 | 25.651 | 0.510 |
| 읽기 90%·쓰기 10% | 2,215 | 6,710 | 12.180 | 9.597 |
| 전체 스캔 혼합 | 1,427 | 6,633 | 47.763 | 9.338 |
| 느린 결과 콜백 혼합 | 1,387 | 6,886 | 59.094 | 9.294 |

전체 지연과 ID 조회 지연을 구분해야 한다. INSERT는 여전히 동기 쓰기 비용과
writer mutex 대기가 있고, 느린 콜백 자체의 50ms 대기는 제거하지 않았다.
개선한 것은 그 작업이 다른 ID 조회까지 장시간 막던 현상이다.

| 16스레드 패턴 | ID 조회 p95 전→후(ms) | INSERT p95 전→후(ms) |
|---|---:|---:|
| 읽기·쓰기 혼합 | 11.163 → 0.131 | 51.611 → 16.434 |
| 전체 스캔 혼합 | 37.746 → 0.135 | 88.641 → 14.615 |
| 느린 콜백 혼합 | 52.900 → 0.133 | 82.618 → 13.442 |

전체 스캔 혼합의 락 대기 p95는 44.896ms에서 8.066ms로 줄었다.
위치 지정 읽기, stdio 랜덤 재충전 제거, 배치 읽기, 잠금 범위 변경을 함께 적용한 결과다.
개별 최적화 하나만의 기여도나 모든 환경에서의 개선 배수로 해석하지 않는다.

모든 비교 케이스에서 오류 0건이었고, 재시작 후 행 수·ID·삽입 내용 검증도 통과했다.
짧은 point 케이스는 전체 실행이 수십 ms에 끝나 변동이 크므로,
긴 ID 조회 검증을 별도로 수행한다.

```powershell
.\build\db_load.exe build/my-million-point 1000000 100000 16 3 1 point
```

100만 행에서 케이스당 10만 요청을 보내는 검증의 원본은
[load-million-point.csv](load-million-point.csv)에 남긴다.

| 스레드 | 처리량 중앙값(req/s) | 실행별 p95 중앙값(ms) |
|---:|---:|---:|
| 1 | 67,585 | 0.0285 |
| 2 | 106,351 | 0.0401 |
| 4 | 108,547 | 0.0831 |
| 8 | 112,229 | 0.1997 |
| 16 | 127,482 | 0.4340 |

5개 동시성 수준 × 3회 × 10만 요청으로 총 **150만 조회**를 추가 검증했다.
오류는 0건이다. 요청 증가에 따라 처리량은 증가했지만 지연도 늘었고,
1→16스레드의 처리량 증가는 약 1.89배였다. 락을 짧게 해도 CPU·OS 파일 I/O와 스케줄러의
비용이 남으므로 스레드 수만큼 선형 확장된다고 볼 수 없다.

원래 2,000요청 비교의 스레드별 처리량과 이 표를 직접 비교하면 안 된다.
초기 데이터 크기와 케이스당 요청 수가 다르며 이 표는 최종 엔진의 추가 검증이다.

## 남은 한계

- INSERT끼리는 직렬화되며 단건 INSERT마다 디스크 동기화한다. 쓰기 부하가 커지면 대기열은 여전히 생긴다.
- 다중 VALUES 배치는 이미 지원하지만 서로 다른 요청을 묶는 group commit은 구현하지 않았다.
- 테이블 인덱스 공개 잠금과 OS 스케줄러·파일시스템·CPU가 남은 병목이 될 수 있다.
- 16스레드가 항상 8스레드보다 빠르다고 보장하지 않는다.
- ASan은 메모리 접근 오류를 검사하지만 데이터 경쟁 검출기는 아니다. ThreadSanitizer 검증은 수행하지 않았다.
- 이 테스트로 서버의 무제한 요청 수용이나 운영 서비스 가용성을 보장하지 않는다.
