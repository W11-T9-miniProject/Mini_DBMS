# DBMS 발표 후보 — 설명 2분 + 실제 데모 2분

**주제:** 파일 저장소에서, 100만 건을 찾아 외부 요청까지 처리하는 미니 DBMS로.

**청중에게 남길 한 문장:** SQL로 기록을 저장하고, 인덱스로 검색할 양을 줄이고, 여러 요청은 스레드 풀과 락으로 처리했다.

## 앞 2분: README를 보며 설명

README의 구현 내용 표 → ID 검색 그림 → 요청 처리 그림 → 검증 결과 순서로 설명한다. 각 부분에서 먼저 “무엇을 직접 구현했는지” 말하고, 그림은 동작을 짚는 데 사용한다. 표나 그림의 문구를 전부 읽지 않는다. 접힌 상세 안내와 아래 진행 지시는 발표자용 자료다.

아래는 읽을 대본 초안이다. 문장 사이에 구조를 가리키는 시간을 포함해 약2분을 목표로 리허설한다.

> 음악 앱에서는 사용자가 재생 버튼을 누르지만, 내부에서는 누가 어떤 노래를 들었는지 기록하고 다시 찾아야 합니다. 저희가 만든 것은 음악 앱 전체가 아니라, 이런 저장과 조회 요청을 처리하는 작은 DBMS입니다.
>
> 첫 단계에서는 SQL 파일을 받아 INSERT와 SELECT를 해석했습니다. 저장할 기록은 파일에 남기고, 조회하면 조건에 맞는 기록을 돌려줍니다. 모든 기록의 길이를 일정하게 정해 파일에서 읽고 쓰는 구조를 단순하게 했습니다.
>
> 두 번째 문제는 검색량입니다. 기록을 하나씩 비교하면 데이터가 많을수록 읽는 양도 많아집니다. 그래서 RAM에 ID와 파일 위치를 연결한 B+ 트리를 만들었습니다. ID로 검색할 때는 트리에서 위치를 찾고 해당 기록만 읽습니다. 실제 기록은 여전히 디스크 파일에 있습니다.
>
> 마지막으로 외부 프로그램이 HTTP로 SQL을 보내도록 연결했습니다. 대기열의 요청을 미리 만든 작업 스레드들이 나눠 처리합니다. 요청 분배와 데이터 보호는 별개입니다. SELECT끼리는 함께 읽지만 INSERT는 파일 저장과 인덱스 갱신, 디스크 반영까지 쓰기 락으로 보호합니다. 쓰기는 순서대로 처리하는 대신 두 데이터가 어긋나지 않도록 했습니다.
>
> 100만 건 검색 비교뿐 아니라 저장·조회 정확성, 노드 분할, 동시 요청, 오류와 메모리 검사도 수행했습니다. 지금부터 실제 서버에 요청해 저장과 검색, 여러 요청의 처리 결과를 보여드리겠습니다. 지원 SQL은 INSERT와 SELECT 중심이고 트랜잭션은 구현 범위에 포함하지 않았습니다.

README에서 가리킬 구조는 이것이면 충분하다.

```text
SQL 요청 → 파서 → 실행 엔진 → 파일 저장소 → 디스크의 실제 기록
                     ↕
                RAM의 ID 인덱스

외부 요청 → HTTP API → 대기열 → 작업 스레드 → 같은 파서·엔진
```

## 뒤 2분: 한 터미널에서 Enter로 세 장면 진행

| 전체 발표 시간 | 실제 조작 | 화면에서 짚을 것·설명 |
| --- | --- | --- |
| 2:00~2:30 | Enter: ① 저장·조회 | “API로 보낸 SQL이 실제 파일에 저장되고, DBMS가 부여한 새 ID로 다시 읽힙니다.” |
| 2:30~3:20 | Enter: ② 검색 비교 | “같은 기록 한 개입니다. ID 인덱스는 파일 기록1건, 전체 탐색은100만 건 이상을 읽습니다. 결과가 다르거나 적어서 빨라진 것이 아닙니다.” |
| 3:20~3:50 | Enter: ③ 동시 요청 | “요청24개를 작업 스레드4개가 처리했습니다. ID 중복·누락 없이 다시 조회됩니다. 저장 자체는 쓰기 락으로 보호합니다.” |
| 3:50~4:00 | 결과 화면에서 마무리 | “저장·검색·외부 요청 처리까지 연결했고, 각 단계의 정확성을 함께 확인했습니다.” |

### 발표 전에 한 번 준비

Mini_DBMS Ubuntu 컨테이너 터미널에서:

```bash
make server benchmark
python3 tools/demo_presentation.py prepare
```

100만 개의 실제 SQL INSERT로 원본92MB를 준비한다. 기본 위치는 data/presentation_dbms이며 Git에는 올라가지 않는다. 준비된 동일 데이터가 있으면 재사용한다. 기존 파일을 덮어쓰지 않는다. 다른 데이터를 쓰려면 새 --directory를 지정한다.

### 발표 때 실행

```bash
python3 tools/demo_presentation.py run
```

별도 임시 복사본과 실제 C HTTP 서버를 사용한다. 기존8091 서버와 충돌하지 않도록 자동 포트를 쓴다. 각 장면에서 Enter를 누르면 실제 요청을 보내고 결과를 보여준다. 반복 실행 시 처음 상태에서 다시 시작하며 기존 연습 DB와 발표용 원본은 변경하지 않는다. 터미널 글씨를 키우고 한 장면씩 읽는다.

### 숫자는 이렇게 설명

- 처음100만 건에 ①에서1개를 추가하므로 ②의 전체 탐색 개수는 **1,000,001개**다. ID 인덱스는 실제 파일 기록1개를 읽는다.
- 화면 시간은 **이번 한 번의 HTTP 왕복·클라이언트 해석 포함 시간**이다. README의 Phase2 내부 검색9회 비교와 측정 범위가 다르다. 발표 때 고정 수치를 암기하지 않고 나온 값을 읽는다.
- ③은 요청 분배·스레드 재사용과 결과 정확성을 보여준다. INSERT 여러 개가 동시에 파일을 변경했다거나 처리량이 몇 배 좋아졌다는 주장은 하지 않는다. SELECT의 실제 중첩은 별도 자동 테스트에서 확인했다.

## 준비물·대안·질문

준비물: Docker/DevContainer, 미리 만든 데이터, 큰 글씨의 터미널과 GitHub README. 네트워크가 필요한 데이터 원본이나 QR 참여는 없다. --auto는 Enter 대기 없이 리허설·검증할 때만 쓴다. 이 도구는 Python 클라이언트이며 DBMS 동작은 기존 C 서버가 수행한다.

2026-11-16 실제100만 건으로 준비·실행을 확인했다. 발표자 대기를 뺀 자동 실행은 약2.5초였고 환경에 따라 달라진다. [사전 실행 기록](presentation-demo-check.json)은 보조 자료이며 현장 실행 결과와 구분한다. 작은 데이터로 반복 실행·원본 보존을 확인하는 준비 도구 테스트2개도 일반/ASan·UBSan 서버에서 통과했다. 실제2분은 발표자 조작·설명 속도로 리허설해야 한다.

실행이 안 되면 준비된 실측 자료를 “사전 검증 결과”라고 명시해 설명하고, 라이브 데모에 성공했다고 말하지 않는다. 시간이 모자라면 핵심인②를 우선하고③을 짧게 설명한다.

Q&A 대비는 세 개만 먼저 준비한다.

- **왜 ID를 파일 위치로 직접 계산하지 않았나?** 현재 고정 길이·연속 ID 조건에서는 가능하다. 이번 과제는 실제 B+ 트리 인덱스의 검색·분할을 구현하는 것이어서 해당 경로를 사용했다.
- **인덱스가 RAM이면 재시작 때는?** 실제 기록은 파일에 남고 시작 시 인덱스를 다시 만든다. 시작 비용이 있다는 한계도 있다.
- **스레드 풀과 락은 무엇이 다른가?** 풀은 요청을 작업자에게 분배하고, 락은 공유하는 파일과 인덱스의 접근을 보호한다.
