# Phase 2 — memory B+ tree index

Approved scope: retain the Phase 1 SQL processor and v2 genre records; add an ID -> file offset memory B+ tree, rebuild on open, and compare >=1,000,000 records. No index persistence, deletion, range SQL, or API/thread pool in this phase.

Nodes hold at most 31 keys. Internal separators route equality right; leaf keys map to offsets and leaves are linked. Overflow splits leaves in half and copies the right minimum upward; internal splits promote the middle separator. Root splitting increases height. Insert supports arbitrary uint64 keys without sentinel restrictions. Duplicate keys are rejected.

Insertion reserves enough spare nodes for a full root-to-leaf split before mutating anything. The engine reserves before appending the file, so index allocation failure cannot leave an acknowledged on-disk INSERT without its index. Spare allocations may remain after a failed reserve but entries are unchanged. Failed storage writes retain the existing storage error policy. Engine open reads validated rows and builds the index, closing/freeing all resources on error.

SQL is unchanged. Valid WHERE id = integer uses the index (at most one file record read); other filters/all rows scan sequentially. Results expose access_path, index_nodes and scanned (file records read, excluding startup). Existing row output and summary are retained. Missing indexed ID is a normal zero-row result, with scanned=0.

Benchmark: generate a SQL file containing 1,000,000 INSERTs with unique event_code and bounded genres, using the Phase 1 parser and engine. In a fresh temporary directory unless --output-dir explicitly supplied, load and sync, close/reopen to validate rebuild, then time paired indexed ID vs unindexed unique event_code lookups returning exactly the same row. Parse outside measured windows; no terminal rows inside query timing, callback checks identity/count. Warm up both paths; report per-query nanoseconds, medians, min/max, records/nodes visited, file size, load/rebuild time. Optimized build; startup, generation, output and sync excluded from lookup measurement. OS cache and local-machine limitations are explicit; this is not a disk-cold/concurrency benchmark.
