SQL은 어떻게
데이터가 될까?

SQL 한 문장이 파싱되고, 실행 계획을 거쳐, 저장 장치의 데이터에 닿는 흐름을 코드와 연결해 봅니다.

한눈에 보는 흐름

SQL 문장 → 파서 → 실행 계획 → 실행기 → 저장소

실제 DBMS는 대체로 이 역할들을 나눠 둡니다. SQLite는 SQL을 바이트코드로 컴파일한 뒤 가상 머신이 실행하고, B-tree와 페이지 캐시를 통해 파일에 접근합니다. SQLite 공식 아키텍처 문서를 참고하세요.

이 프로젝트에 대입하기

예를 들어 다음 조회를 생각해 봅시다.

SELECT name FROM people WHERE age >= 18;

1. 파싱 — engine.c의 next()가 토큰을 읽고 select_rows()가 SELECT 문법을 처리합니다. WHERE 조건은 parse_atom(), parse_and(), parse_or()가 구조로 만듭니다.

2. 논리 작업 — 의미상 “people을 읽고 → age 조건을 적용하고 → name만 남긴다”입니다. 현재 코드는 이 계획을 별도 객체로 만들지 않습니다.

3. 실행과 저장소 — select_rows()가 people.rows를 순서대로 읽도록 db_read()를 부르고, matches()로 조건을 검사한 뒤 결과를 출력합니다.

즉, 이 미니 DBMS에서는 파싱부터 실행까지가 select_rows() 안에서 바로 이어집니다. 실제 DBMS에서 따로 나누는 단계가 이 코드에서는 합쳐져 있는 셈입니다.

기억할 한 가지

논리 계획은 “무슨 작업인가”, 물리 실행은 “그 작업을 실제로 어떤 방식으로 할까”입니다.

논리적으로는 Scan → Filter → Project이고, 이 프로젝트의 물리 방식은 파일 전체를 순차 읽는 것입니다.
