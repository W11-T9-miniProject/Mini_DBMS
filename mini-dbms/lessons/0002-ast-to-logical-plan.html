AST에서
논리 계획으로

SQL의 문법 구조를 DBMS 작업들의 조합으로 바꾸는 법을 익힙니다.

둘은 무엇이 다를까?

AST는 SQL에 어떤 문법 요소가 쓰였는지 표현합니다. 논리 계획은 그 SQL이 어떤 데이터 작업을 뜻하는지 표현합니다.

SQL:
SELECT name FROM people WHERE age >= 18;

AST (단순화):
Select
├── columns: [name]
├── table: people
└── where: age >= 18

AST는 SQL 문장에 가까운 모양이에요. 여기서 테이블과 컬럼이 실제로 존재하는지 확인한 다음, 관계 연산으로 옮깁니다.

논리 계획으로 바꾸기

Project[name]
└── Filter[age >= 18]
    └── Scan[people]

아래에서 위로 읽으면 “people을 읽고, 조건을 거르고, name만 남긴다”는 뜻입니다.

Scan — 테이블의 행을 가져온다.

Filter — 조건에 맞는 행만 통과시킨다.

Project — 결과에 필요한 컬럼만 남긴다.

이 계획은 아직 파일이나 인덱스를 지정하지 않아요. 같은 논리 계획을 전체 스캔으로도, 인덱스 사용으로도 실행할 수 있습니다. SQLite 공식 아키텍처 문서는 파서가 만든 parse tree를 분석해 실행용 코드를 생성하는 과정을 설명합니다. SQLite 아키텍처

이 프로젝트 코드와 비교

현재 engine.c의 parse_atom()은 age >= 18 같은 비교식을 Expr 노드로 만들고, parse_and()와 parse_or()가 조건 노드를 연결합니다. 이건 WHERE 조건의 AST와 비슷한 구조예요.

하지만 전체 SELECT AST와 논리 계획은 따로 만들지 않습니다. select_rows()가 SELECT를 파싱한 직후 파일을 열어 스캔하고, 조건 평가와 결과 컬럼 출력을 이어서 합니다.

현재 코드의 실제 흐름:
SELECT 파싱 → .rows 순차 읽기 → matches() → 선택 컬럼 출력

개념상 논리 계획:
Project[name] → Filter[age >= 18] → Scan[people]

따라서 논리 계획은 현재 코드에 이미 존재하는 객체의 이름이 아니라, 현재 동작을 DBMS 개념으로 설명한 모델입니다.
