행에서 페이지로

DBMS는 디스크의 데이터를 보통 한 행씩이 아니라, 페이지라는 묶음 단위로 가져옵니다.

먼저 파일 둘을 구분하기

스키마 (people.schema) — 테이블이 어떤 모양인지 적은 구조 정보. 예: id INTEGER, name TEXT.

행 데이터 (people.rows) — 실제 값들. 예: 1, Mina, 2, Joon.

스키마는 “각 행에 어떤 칸이 있는가”를 알려주고, 데이터 파일은 “각 칸에 실제로 어떤 값이 들어 있는가”를 담습니다.

페이지는 데이터의 운반 상자

디스크에서 작은 값 하나만 매번 요청하면 비효율적입니다. 그래서 DBMS는 파일의 일정한 크기 구간을 페이지로 다루고, 페이지 안에 여러 행이나 인덱스 항목을 저장합니다.

데이터베이스 파일
┌──────────┬──────────┬──────────┐
│ 페이지 0 │ 페이지 1 │ 페이지 2 │ ...
│ 여러 행  │ 여러 행  │ 여러 행  │
└──────────┴──────────┴──────────┘

실행기는 “이 행을 줘”라고 요청하지만, 저장 계층은 필요한 페이지를 메모리에 올리고 그 안에서 행을 찾아 줄 수 있어요.

페이지 캐시는 무엇을 하나?

페이지 캐시는 최근에 읽었거나 수정한 페이지를 메모리에 보관합니다. 같은 페이지를 다시 요청하면 디스크를 재차 읽지 않고 메모리의 복사본을 쓸 수 있어요.

실행기 요청 → 페이지 캐시 확인
                 ├─ 이미 메모리에 있음 → 바로 전달
                 └─ 없음 → 파일에서 페이지 읽기 → 캐시에 보관

SQLite의 공식 아키텍처 문서에 따르면 B-tree 모듈은 페이지를 페이지 캐시에 요청하고, 페이지 캐시는 필요한 페이지를 디스크에서 읽어오며 트랜잭션과 잠금 관련 역할도 담당합니다. SQLite 아키텍처: Page Cache

이 프로젝트와 실제 DBMS의 차이

이 프로젝트는 페이지 캐시 계층 없이 db_read()가 .rows 파일에서 직렬화된 행을 직접 읽습니다. 따라서 앞 수업의 순차 스캔은 파일을 행 단위 형식으로 훑는 방식이에요.

실제 DBMS에서는 대개 실행기와 파일 사이에 저장소 계층이 있고, 페이지 단위 읽기·캐싱·쓰기·복구를 담당합니다. 그래서 이 프로젝트의 db_read()를 실제 DBMS의 전체 저장소 계층과 동일시하면 안 됩니다. 행을 해석하는 작은 저장 함수에 더 가깝습니다.
