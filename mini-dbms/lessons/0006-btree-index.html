B+트리 인덱스는
어떻게 찾을까?

인덱스는 값과 행 위치를 정렬된 구조로 보관해 검색 범위를 빠르게 좁힙니다.

책의 찾아보기와 비슷하지만

책의 찾아보기가 단어에서 페이지 번호를 알려주듯, 데이터베이스 인덱스는 키 값에서 행을 찾을 정보를 제공합니다.

age 인덱스의 개념 예:
18 → 행 위치 A
21 → 행 위치 B
35 → 행 위치 C

실제 DBMS의 인덱스는 보통 디스크 페이지에 저장되고, 각 항목에는 키와 행을 찾을 정보가 들어갑니다.

B+트리는 무엇을 더하나?

B+트리는 키를 정렬해 여러 갈래의 트리 페이지에 배치합니다. 위쪽 페이지에서 검색 범위를 좁히고, 마지막에는 리프 페이지에서 키를 찾습니다. 리프 페이지들은 키 순서로 이어져 있어 범위 조회도 효율적으로 읽을 수 있습니다.

                 [ 20 | 40 ]       내부 페이지
                /    |     \
         [5,12]  [20,31]  [40,58]   리프 페이지
             ─────→─────→─────      범위 순회

age = 31이면 루트에서 해당 범위로 내려갑니다. age >= 20이면 알맞은 리프부터 뒤쪽 리프를 순서대로 훑을 수 있어요.

SQLite 공식 구조 설명에서는 데이터베이스 파일이 B-tree로 관리되고, B-tree 모듈이 페이지 캐시에 페이지를 요청한다고 설명합니다. SQLite 아키텍처

테이블 데이터와 인덱스는 따로 유지

인덱스는 보조 구조예요. 원본 행은 테이블에 있고, 인덱스는 키와 행을 찾아갈 정보를 따로 둡니다. 그래서 `INSERT`하면 테이블 행뿐 아니라 관련 인덱스도 갱신해야 합니다. 인덱스를 많이 만들수록 조회가 빨라질 수 있지만, 저장 공간과 쓰기 작업도 늘어요.

최적화기는 조건과 비용 추정치를 보고 인덱스를 쓸지 전체 스캔을 할지 고릅니다. 인덱스가 있다고 매번 쓰는 것은 아닙니다.

현재 프로젝트에는 없음

이 프로젝트의 .rows 파일은 행을 순서대로 저장하고, 인덱스 파일이나 B+트리 구현은 없습니다. 따라서 SELECT ... WHERE age = 31도 처음부터 행을 읽으며 조건을 검사합니다.
