SELECT 한 문장의
전체 여정

배운 아키텍처 요소를 하나의 쿼리에 연결하고, 실제 DBMS와 미니 DBMS의 경계를 구분합니다.

예제로 따라가기

SELECT name FROM people WHERE age >= 18;

질문은 “people에서 age가 18 이상인 행의 name을 보여줘”입니다. 이 문장은 대략 다음 여정을 거칩니다.

실제 DBMS에서의 개념적 흐름

SQL 문장
  ↓ 파싱: 문법 구조(AST)
논리 계획: Scan → Filter → Project
  ↓ 최적화: 통계와 인덱스로 방법 선택
물리 계획: 예) people 테이블 순차 스캔
  ↓ 실행기
페이지/버퍼/인덱스/트랜잭션 계층
  ↓
결과 행

각 단계가 반드시 물리적으로 분리된 함수나 프로세스라는 뜻은 아니지만, 역할을 구분하면 DBMS 동작을 이해하기 쉬워집니다. SQLite도 SQL을 바이트코드로 컴파일하고 가상 머신에서 실행하며, B-tree와 페이지 캐시로 데이터에 접근합니다. SQLite 공식 아키텍처

미니 DBMS에서 실제로 일어나는 일

main.c: SQL 파일을 읽음
  ↓
db_execute(): 토큰을 읽고 SELECT로 분기
  ↓
select_rows(): 테이블/컬럼 확인, WHERE 파싱,
              .rows 파일을 열고 전체 순회
  ├─ db_read(): 다음 행 복원
  ├─ matches(): WHERE 조건 검사
  └─ write_field(): 통과 행의 name 출력

있는 것: SQL 토큰화, SELECT 처리, 조건식 노드, 행 직렬화/복원, 파일 순차 스캔.

아직 없는 것: SELECT 전체 AST, 별도 논리 계획 객체, 비용 기반 최적화기, 인덱스/B+트리, 페이지 캐시, 트랜잭션 복구, 동시성 제어.

여기서 핵심은 이름을 억지로 붙이는 게 아니라, 코드가 실제로 하는 일과 DBMS에서 보통 분리하는 역할을 비교하는 것입니다.
