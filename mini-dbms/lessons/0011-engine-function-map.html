엔진 함수는
어떻게 이어질까?

SQL 진입점인 db_execute()에서 SELECT와 INSERT의 함수 흐름을 따라갑니다.

바깥에서 안쪽으로

main()은 SQL 파일을 메모리로 읽은 뒤 db_execute()를 호출합니다. 엔진의 중심 함수는 SQL 문자열을 토큰으로 읽고 문장 종류에 따라 처리 함수를 부릅니다.

main()
  └── db_execute()
      ├── next()       다음 토큰 읽기
      ├── insert()     INSERT 처리
      └── select_rows() SELECT 처리

db_execute()는 작은 문장 분배기라고 생각하면 됩니다. SQL 문법 전체를 직접 수행하는 대신 다음 단계의 함수를 선택합니다.

SELECT의 함수 흐름

select_rows()
  ├── open_table() ── db_table_open()   .schema 읽기
  ├── parse_or()
  │    └── parse_and()
  │         └── parse_atom()            WHERE 구조 만들기
  └── .rows 파일 열기
       ├── db_read()                    행 복원
       ├── matches()                    조건 검사
       └── write_field()                출력 형식 만들기

함수마다 책임이 있습니다. db_table_open()은 테이블 구조를 읽고, db_read()는 행을 복원하며, matches()는 행이 조건에 맞는지 계산합니다.

INSERT의 함수 흐름

insert()
  ├── open_table() ── db_table_open()  컬럼/타입 확인
  ├── identifier(), literal()          이름과 값 파싱
  └── db_append()                       행을 .rows 끝에 저장

insert()가 SQL 입력을 해석하고 유효성을 확인한 뒤, 실제 직렬화와 파일 쓰기는 저장 계층의 db_append()에 맡깁니다.

아키텍처상 중요한 경계

engine.c는 SQL을 이해하고 실행 흐름을 조정합니다. storage.c는 스키마와 행 파일에 접근합니다. 이 둘의 경계 덕분에 SQL 처리 코드가 파일 직렬화 세부사항을 전부 직접 구현하지 않아도 됩니다.

다만 현재 select_rows()는 파싱, 파일 스캔, 필터링, 결과 출력을 한 함수에서 이어서 합니다. 실제 DBMS식으로 더 나누려면 AST와 논리 계획, 실행 연산자, 저장소 인터페이스를 별도 단계로 둘 수 있습니다.

호출 흐름을 이해할 때는 “누가 문장을 해석하나?”, “누가 행을 읽나?”, “누가 조건을 평가하나?”를 각각 찾으면 됩니다.
