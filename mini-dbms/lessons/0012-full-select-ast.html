조건만 말고
SELECT 전체를 담기

AST를 중간 결과로 두면 SQL 파싱과 실제 실행을 분리할 수 있습니다.

현재는 WHERE 조건만 구조화

현재 코드의 Expr는 age >= 18 같은 비교나 AND/OR 연결을 표현합니다. 하지만 SELECT 컬럼 목록, 테이블 이름, 문장 전체를 한 객체에 담지는 않아요. select_rows()가 SQL을 읽으면서 곧바로 파일을 열고 실행합니다.

SELECT name FROM people WHERE age >= 18;
                      └── 현재 구조화되는 부분: age >= 18

문장 전체 AST의 모양

파싱 결과를 하나의 SelectStmt에 모은다고 생각해 봅시다.

struct SelectStmt {
    char *table_name;       // "people"
    size_t projection[];    // [name 컬럼]
    Expr *where;            // age >= 18 조건 트리
};

그러면 파서의 일은 이 구조를 만드는 데서 끝납니다. 이 단계에서는 아직 .rows 파일을 열지 않아요.

왜 중간 구조를 둘까?

파서: SQL 문법을 읽어 AST를 만든다.

검증기: 테이블과 컬럼이 존재하는지, 타입이 맞는지 확인한다.

계획기: AST를 Scan/Filter/Project 같은 논리 작업으로 바꾼다.

실행기: 선택된 계획을 실제 저장소에서 수행한다.

각 단계가 다음 단계에 명확한 자료를 넘겨주므로, 파서를 바꾸거나 인덱스 계획을 추가해도 한 함수의 모든 일을 다시 고칠 필요가 줄어듭니다.

흐름 비교

현재:
SQL 읽기 + 검증 + 파일 스캔 + 필터 + 출력
                 대부분 select_rows()에서 진행

분리한 설계:
SQL → SelectStmt AST → 논리 계획 → 물리 계획 → 실행기

AST는 실행 계획 자체가 아닙니다. AST는 SQL 문장의 구조이고, 논리 계획은 그 구조가 뜻하는 데이터 연산입니다.
