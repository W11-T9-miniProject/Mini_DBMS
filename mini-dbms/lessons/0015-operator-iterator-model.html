연산자가 서로에게
행을 요청한다

많은 DBMS 실행기는 연산자들을 트리로 연결하고, 위쪽에서 아래쪽으로 다음 행을 요청하는 방식을 사용합니다.

공통 인터페이스의 생각

각 물리 연산자가 같은 약속을 따른다고 상상해 보세요.

open()   준비
next()   다음 결과 행을 달라
close()  사용한 자원 정리

실행기는 루트 연산자에 next()를 요청합니다. 루트가 결과를 만들려면 자식에게도 next()를 요청하고, 그 요청이 아래 저장소까지 전달됩니다. 이 방식을 iterator/pull 모델이라고 부릅니다.

Filter는 자식에서 행을 가져와 검사

Project.next()
  └─ Filter.next()
       ├─ SeqScan.next() → age=12 행: 버림
       ├─ SeqScan.next() → age=18 행: 통과
       └─ Project가 name만 반환

Filter는 한 행을 받아 조건을 확인하고, 맞지 않으면 다음 행을 다시 요청합니다. 맞는 행을 만나면 위쪽에 반환합니다. Project는 그 행에서 요청된 컬럼만 내보냅니다.

이 방식의 좋은 점

조합 가능: 같은 Filter를 SeqScan 위에도, IndexScan 위에도 붙일 수 있다.

필요할 때 계산: 결과를 전부 한꺼번에 메모리에 만들지 않고 행씩 처리할 수 있다.

책임 분리: 스캔, 조건 검사, 컬럼 선택을 각 연산자가 맡는다.

예를 들어 Project → Filter → SeqScan의 각 노드는 아래 노드가 어디서 행을 구하는지 알 필요 없이 공통 인터페이스를 통해 행을 요청합니다.

현재 프로젝트와 비교

현재 select_rows()의 반복문이 이 연산자들의 일을 한곳에서 직접 합니다. db_read()가 행을 가져오고, matches()가 조건을 검사하고, 출력 부분이 필요한 컬럼을 내보내죠. iterator 인터페이스를 도입하면 이 동작을 별도 노드로 나눌 수 있지만, 현재 코드에는 그런 객체나 next() 인터페이스가 없습니다.

현재: 한 함수 안의 반복문

분리 후 개념:
Project.next() → Filter.next() → SeqScan.next()
