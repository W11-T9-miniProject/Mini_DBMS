행 하나씩 말고
묶음으로 계산하기

벡터화 실행은 연산자가 한 행씩 주고받는 대신, 여러 행을 담은 작은 묶음을 함께 처리하는 방식입니다.

행 단위 처리

단순한 실행기는 행을 하나씩 읽고 조건을 검사합니다.

row 1 읽기 → age 비교
row 2 읽기 → age 비교
row 3 읽기 → age 비교
... 반복

이 방식은 이해하기 쉽지만, 많은 행에서 함수 호출과 분기 처리를 반복할 수 있습니다.

벡터 단위 처리

벡터화 실행기는 같은 타입의 여러 값을 배열처럼 모아 조건을 한꺼번에 계산합니다. 예를 들어 age 값 4개가 한 벡터에 있으면, 조건 결과도 여러 개의 참/거짓으로 구할 수 있습니다.

age 벡터:       [12, 18, 25, 9]
age >= 18 결과: [ F,  T,  T, F ]

Project[name]: 통과한 행의 name 값만 추림

DuckDB는 고정 크기 벡터들을 담는 DataChunk를 연산자 사이에 전달합니다. 공식 문서의 기본 벡터 크기 예시는 2048행입니다. DuckDB Execution Format

왜 빠를 수 있을까?

한 번의 연산 호출로 여러 값을 처리해 행마다 발생하는 호출 비용을 줄일 수 있습니다.

값들을 메모리에서 연속된 배열로 다루면 CPU 캐시와 벡터 명령을 더 잘 활용할 수 있습니다.

청크 단위로 처리하면 전체 결과를 한꺼번에 메모리에 올리지 않고도 대량 데이터를 다룰 수 있습니다.

항상 무조건 빠른 것은 아니며 데이터 형식, 연산 종류, 메모리 구조에 따라 이점이 달라집니다.

Push 방식과 결합될 수도 있다

DuckDB는 공식 내부 구조 문서에서 DataChunk를 연산자 트리를 따라 밀어 보내는 push 기반 벡터화 모델을 설명합니다. 즉 “여러 행을 묶어 처리”하는 벡터화와 “아래에서 위로 전달”하는 push는 서로 다른 설계 축이지만 함께 쓸 수 있습니다. DuckDB 내부 구조 개요

미니 DBMS와 비교

현재 db_read()는 행 하나를 복원하고, matches()가 그 행의 조건을 검사합니다. 이 프로젝트는 벡터나 DataChunk를 전달하지 않으므로 행 단위 처리입니다.

현재: db_read → matches → 출력 (한 행씩)
벡터화 설계: read_chunk → filter_chunk → project_chunk
                              (여러 행씩)

“벡터화 실행”의 벡터는 여러 행의 값 배열을 뜻합니다. 임베딩으로 유사도를 찾는 벡터 데이터베이스의 벡터와는 다른 개념이에요.
