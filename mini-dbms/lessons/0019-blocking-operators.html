왜 어떤 연산은
행을 기다릴까?

Blocking 연산자는 결과를 내기 전에 입력의 많은 부분 또는 전부를 먼저 살펴야 합니다.

필터는 보통 바로 흘려보낼 수 있다

age >= 18 필터는 행 하나를 받으면 그 행만 검사하면 됩니다. 통과한 행은 즉시 다음 연산자로 보낼 수 있어요.

행 도착 → 조건 검사 → 통과하면 즉시 출력
             (다음 행을 기다릴 필요 없음)

정렬은 입력을 먼저 모은다

전체 행을 이름순으로 출력하려면 뒤에 더 작은 이름이 남아 있는지 알아야 합니다. 일반적인 전체 정렬은 모든 입력을 모으고 정렬한 다음 첫 결과를 내보냅니다.

입력 행 전부 수집 → 정렬 → 첫 결과부터 반환

메모리에 다 담기지 않으면 DBMS는 정렬 데이터를 임시 디스크 공간에 나눠 저장하고 병합할 수 있습니다. PostgreSQL의 EXPLAIN은 정렬이 메모리에서 수행됐는지 디스크를 사용했는지 보여줄 수 있습니다. PostgreSQL EXPLAIN

해시 조인은 먼저 한쪽을 준비한다

해시 조인은 한쪽 테이블을 읽어 조인 키로 해시 테이블을 만든 뒤, 다른 쪽 행을 읽으며 일치 항목을 찾습니다. 첫 결과를 만들기 전에 build 쪽 입력을 읽어 구조를 준비해야 합니다.

build 입력 전체 → 해시 테이블 구성
probe 입력 행 → 해시 테이블에서 일치 검색 → 결과

PostgreSQL 문서도 한쪽 행을 메모리 해시 테이블에 넣고, 다른 쪽을 스캔하며 일치 여부를 탐색하는 계획으로 설명합니다. Hash Join 설명

Blocking의 대가와 이유

대가: 첫 결과가 늦어질 수 있고, 메모리나 임시 디스크 공간이 필요할 수 있습니다.

이유: 정렬된 순서나 여러 입력 간 일치 여부처럼, 앞선 입력만으로 결정할 수 없는 결과를 계산해야 합니다.

모든 blocking 연산이 무조건 나쁘다는 뜻은 아닙니다. 쿼리 결과에 정렬이나 조인이 필요하면 그 의미를 만족시키기 위한 작업입니다. 최적화기는 비용과 메모리 사용을 고려해 방법을 선택합니다.

현재 미니 DBMS에서는

현재 SQL에는 ORDER BY와 JOIN이 없으므로 정렬·해시 조인 연산자가 없습니다. 기본 SELECT의 파일 순회와 필터는 행을 읽는 대로 처리하고 바로 출력합니다.
