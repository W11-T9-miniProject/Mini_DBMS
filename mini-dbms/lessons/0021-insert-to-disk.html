INSERT는 어떻게
파일에 저장될까?

SQL의 값들이 검증되고 직렬화되어 행 파일 끝에 추가되는 경로를 따라갑니다.

입력 SQL

INSERT INTO people (id, name, age)
VALUES (7, 'Mina', 24);

main()이 SQL 파일을 읽고, db_execute()가 INSERT 키워드를 만나 insert()로 분기합니다.

1. 스키마로 컬럼과 타입 확인

insert()가 open_table()을 통해 db_table_open()을 호출합니다. 저장 계층은 people.schema를 읽어 컬럼 이름과 타입을 DbTable에 채웁니다. 이 정보로 SQL의 컬럼 이름과 입력 리터럴을 검사합니다.

people.schema
id INTEGER
name TEXT
age INTEGER

이 프로젝트에서는 사람이 미리 준비한 스키마 파일을 읽는 방식입니다. 아직 CREATE TABLE로 등록하지 않습니다.

2. SQL 값에서 메모리 행으로

insert()는 컬럼 이름을 내부 컬럼 번호로 찾고, literal()은 타입에 맞는 값을 파싱합니다. 정수는 범위를 확인하고 표준 문자열 형태로 만들며, 텍스트는 줄바꿈 같은 저장 형식상 허용되지 않는 내용을 거릅니다.

DbRow {
  values[0] = "7",
  values[1] = "Mina",
  values[2] = "24"
}

3. 행을 바이트로 직렬화

db_append()는 각 값의 길이를 4바이트 정수로 기록한 뒤, 값의 바이트를 이어 붙입니다. 예를 들면 다음처럼 저장됩니다.

[길이 1][문자 '7']
[길이 4][문자 'Mina']
[길이 2][문자 '24']

이런 식으로 메모리의 값을 파일에 저장 가능한 바이트 배열로 바꾸는 일을 직렬화라고 합니다. 이후 db_read()는 길이를 읽어 각 값을 다시 복원합니다.

4. 파일 끝에 추가

직렬화가 끝나면 db_append()가 .rows 파일을 append 모드로 열고 바이트를 씁니다. 여기서 중요한 설계 특징은 행 파일은 컬럼 이름을 저장하지 않고, 스키마 순서대로 값만 저장한다는 점입니다. 그래서 기존 행을 해석하려면 같은 스키마 순서가 유지되어야 합니다.

이 단순 구현에는 WAL/롤백, 동시 쓰기 제어, 행 단위 체크섬 같은 안정성 기능이 없습니다. 따라서 DBMS가 보장하는 완전한 트랜잭션 저장이라고 보면 안 됩니다.
