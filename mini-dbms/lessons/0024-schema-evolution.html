컬럼을 추가하면
옛 행은 어떻게 될까?

스키마만 바꾸면 데이터 파일이 새 구조와 어긋날 수 있습니다. 저장 형식이 이 상황을 어떻게 지원하는지가 중요합니다.

현재 포맷은 스키마 순서에 의존

미니 DBMS의 db_append()는 값들의 길이와 바이트를 컬럼 순서대로 씁니다. 행 파일 자체에는 컬럼 이름이나 행의 컬럼 수를 기록하지 않습니다. db_read()는 현재 스키마의 컬럼 수만큼 값을 읽습니다.

기존 스키마: id, name
기존 파일 행: [id 값][name 값]

새 스키마: id, name, age
읽는 쪽 기대: [id 값][name 값][age 값]

예전 행에는 age 값이 없습니다. 스키마 파일만 바꾸면 읽는 쪽이 다음 행의 바이트를 age 값으로 착각하거나 파일 끝에서 손상 오류를 낼 수 있습니다.

안전한 변경의 선택지

기존 행 재작성: 옛 포맷으로 읽고 새 컬럼의 기본값을 채운 다음 새 포맷으로 모든 행을 기록한다.

포맷에 버전·컬럼 수 추가: 각 행의 레이아웃을 알아볼 수 있게 하고, 옛 행에 기본값을 적용한다.

마이그레이션 임시 파일: 새 파일을 완성한 뒤 안전하게 교체해 중간 실패가 원본을 망가뜨리지 않게 한다.

어떤 방법이든 실패 복구와 원자적인 교체를 고려해야 합니다. 단순히 스키마 텍스트만 수정하는 것으로 충분하지 않을 수 있어요.

실제 DBMS는 모두 같은 방식이 아니다

SQLite의 파일 형식은 기존 레코드가 새로 추가된 컬럼 값을 갖지 않을 수 있게 설계되어 있습니다. 새 스키마가 기본값을 적용해 예전 행을 해석할 수 있어, ADD COLUMN이 항상 모든 행을 다시 쓰는 것은 아닙니다. 이는 SQLite 파일 형식의 구체적인 설계예요. SQLite File Format · SQLite ALTER TABLE

반면 이 미니 DBMS의 행 포맷은 컬럼 개수와 버전 정보를 담지 않으므로 그런 해석 기능이 없습니다.

아키텍처에서 배울 점

DDL은 카탈로그의 구조만 바꾸는 일이 아니라, 기존 저장 데이터를 새 구조와 일치시키는 작업일 수 있습니다. 그래서 실제 DBMS는 메타데이터 변경, 데이터 변환, 인덱스 갱신, 트랜잭션 복구를 함께 설계합니다.
